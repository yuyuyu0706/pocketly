## 1. 判定基準（Charter §6 より再掲）

```text
■ Step 1: ゲート条件（該当すれば即・優先度-高。規模や閲覧貢献度で薄めない）
  a) 現在すでに壊れている（利用者が期待どおりに使えない）
  b) コンセプト実現の中核である（主用途 C を成立させる施策そのもの。規模を問わない）
  c) 安全性・可用性に関わる（外部依存の破壊的変更、未サニタイズ等）

■ Step 2: ゲート非該当の課題を判定する 2 軸マトリクス

                        | 開発規模：軽量(S) | 開発規模：重量(M〜L)
  閲覧体験向上：高      | 優先度-高（クイックウィン） | 優先度-中（計画的投資）
  閲覧体験向上：低      | 優先度-小                   | 対象外の候補

■ Step 3: 土台性（独立軸・Phase 振り分け専用）
  土台性-高 = 2 件以上の他課題の前提、または後回しで作り直しが発生
             → 優先度に関わらず Phase 2 へ配属
```

規模: S = 1 日以内 / M = 数日 / L = 1 週間超

### 追加運用ルール（Lv2-C 確定）

**ルール 1: 土台性-高の課題はマトリクス適用除外**

土台性-高の課題（MDE-008/009/023/024/025）は 2 軸マトリクスの評価対象外とし、優先度を一律「高（基盤）」として確定する。ラベル表記は「高（基盤）」とし、閲覧体験由来の「高」と区別する。

**ルール 2: 「編集体験→閲覧体験への波及」を閲覧体験向上度の評価に含める**

編集のしやすさが最終的な文書の完成度（読者が目にする成果物の質）へ直接波及する場合、その波及効果を「閲覧体験向上度」の評価に含めてよい。新しいゲート条件は設けず、既存の 2 軸マトリクスにおける「閲覧体験向上度」の判定材料として扱う。

- 波及が強い（編集の質が成果物の完成度に直結する）→ 高評価に含めてよい（例: MDE-005、MDE-020）
- 波及が弱い（編集効率の一般的改善に留まる）→ 従来どおり低評価（例: MDE-015、MDE-018、MDE-022）

#### MDE-023 テキスト編集処理が 12 箇所に重複し undo を壊す

| 項目 | 内容 |
| --- | --- |
| 分類 | 基盤 |
| 事象 | 本文を書き換える処理が 12 箇所に個別実装されており、いずれも `editor.value` 直接代入のためブラウザの undo スタックを破棄する |
| 原因 | `script.js:434` / `545` / `992` / `1194` / `1249` / `1313` / `1428` / `1806` / `2365` / `2419`、`js/preview.js:477` / `481` |
| 影響 | `MDE-004` の直接原因。また同じ「値の差し替え → ハイライト更新 → AppState 反映 → 行番号更新 → フォーカス復帰」の定型処理が全箇所にコピーされており、装飾を 1 つ追加するたびに定型を再実装する必要がある |
| 規模 | M |
| 土台性 | **高** — `MDE-004` / `005` / `015` / `019` / `020` の前提 |
| 方針案 | 共通ユーティリティ `replaceEditorRange(start, end, text)` を新設。内部で `setSelectionRange()` → `document.execCommand('insertText', ...)` を使い、`input` イベント経由の変更にすることでネイティブ undo に載せる。非対応環境は現行の直接代入へフォールバック |
| 判定根拠 | 土台性-高（2 件以上の前提）のため 2 軸マトリクス適用除外。優先度「高（基盤）」として Phase 2 に強制配属 |
| 備考 | `execCommand` は deprecated だが、textarea の undo 連携を保つ実用手段は現状これのみ。将来的な `EditContext` API への移行余地をコメントで残すこと |

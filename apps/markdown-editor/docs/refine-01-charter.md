### 背景

Markdown Editor は Pocketly の中で最も機能が厚いアプリであり、ライブプレビュー・Mermaid・目次・テンプレート・多言語といった資産が既にある。一方で以下の状況にある。

- 利用時に体感される不具合・使いにくさが複数残っている（印刷、Undo、表の可読性、画面の窮屈さ）
- 「Excel / Word から Markdown へ移行する」という利用者側の行動変容が起きていない
- `script.js` が 2,769 行の単一クロージャに集中しており、改修のたびに影響範囲の見極めコストが発生する

個別の修正を場当たり的に積むのではなく、**課題の全体像を一度棚卸しし、優先度と将来構想を確定させたうえで実装フェーズへ入る**ことを目的として本 PJ を立ち上げる。

### PJ ゴール（Phase 6 到達時の姿）

1. 既知の不具合が解消され、日常利用でストレスを感じない状態になっている
2. 「Markdown で資料を作りたい」「Markdown を快適にプレビューしたい」と感じられる体験上の武器が最低ひとつ確立している
3. 追加改修が安全に行える構造（責務分割・テスト・依存管理）になっている
4. 本 Refine でやらないと判断した構想が、判断理由とともに記録されている

### Phase 2 と Phase 3 の切り分け方針

Phase 2 を「基盤整備」として独立させたことで、**同一ファイルを Phase をまたいで作り直す手戻り**を回避する設計になっている。振り分け基準は以下とする。

- **Phase 2 に入るもの** — それ自体は利用者から見えないが、複数の後続課題がその上に乗るもの。責務分割、共通ユーティリティ化、依存バージョン固定、テスト土台、スタイル構造の分離など
- **Phase 3 に入るもの** — 利用者が挙動の変化を体感できるもの

判定に迷う課題は、後述の「土台性」評価で決める。

## 3. コンセプト定義

> ⚠ 本節は Phase 1 の最重要意思決定項目。ここが決まらないと優先度判定が主観的になる。

### 3-1. コンセプト文（確定）

> **開いた瞬間から読みやすく、書き始めたくなる。ブラウザだけで完結する Markdown ドキュメントツール。**

主用途 C（閲覧既定・編集は明示的呼び出し）の決定と整合するため、叩き台のまま確定する。（決定: Issue #51）

### 3-2. 想定利用者と主用途（確定: C）

現状のアプリは「書く人」と「読む人」の両方を1画面で扱っており、それが窮屈さの原因にもなっている。どちらを主とするかで、Phase 2 以降の設計が分岐する。

| 選択肢 | 主用途 | 設計上の帰結 |
| --- | --- | --- |
| A. 作成主体 | 資料を Markdown で作り、配布物として出力する | 印刷品質・表編集・書き心地が最優先。エディタが常設 |
| B. 閲覧主体 | 受け取った `.md` を快適に読む | プレビュー品質・目次・検索が最優先。編集は副次的 |
| **C. 閲覧を既定とし、編集は明示的に呼び出す** ✅ **確定** | 読むために開き、必要になったら書く | モード制レイアウト。既存の改善要望（画面の窮屈さ）と整合 |

**C に確定。** 理由：一般論として読み手は書き手より圧倒的に多く、「閲覧」を入口戦略とするほうが多くの人の課題にアプローチできる。また「Markdown ファイルをストレスなくプレビューしたい」という実務要望・「1 ウィンドウで 3 ペインは窮屈」という指摘の双方と一致する。（決定: Issue #51）

### 3-3. 「シンプル」の定義（確定: N_read=5 / N_edit は運用ルールで制御）

「シンプルさを維持する」を判断可能な基準に落とす。（決定: Issue #51）

- **画面のシンプルさ（閲覧モード）**: `N_read = 5`。閲覧モード（既定）で常時表示される操作要素の上限。「折りたたみ状態でも常時見えている最上位の操作項目数」と定義し、配置方法（横ツールバー／サイドバーレール等）には依存しない
- **画面のシンプルさ（編集モード）**: `N_edit = 上限なし（運用ルールで制御）`。編集モードは現状 9 個を基準とするが数値上限は設けない。機能追加時は §6-3 コンセプト適合チェック（① 主用途への貢献 ② シンプルさ違反の有無 ③ 既存機能で代替できないか）を通過することを条件とする
- **設定のシンプルさ**: 利用者が設定する項目を増やさない。増やす場合は既定値のままで成立させる
- **機能のシンプルさ**: 機能を1つ足すときは、代替できる既存機能がないかを必ず確認する
- **判断基準**: 初見の利用者が説明なしに使えるか

> **理由**: 「シンプル」の実感は最初に開く画面（閲覧モード）で決まるため、既定画面にこそ強い制約を適用する。編集は「明示的に呼び出す」機能であり、そこでの機能充実は「シンプルさ違反」に当たらない。単一の `N` を全体適用すると機能追加のたびに不毛な数合わせ議論が生じるため、モード別に分離した。

### 3-4. 非目標（Non-Goals）

以下は本 PJ の目標としない。将来構想としては記録する。

- 複数ファイル管理・文書間リンク・横断検索（ドキュメント管理ツール化）
- サーバーサイド機能、アカウント、同期
- 共同編集
- `packages/` `shared/` 等の Pocketly 共通化基盤の先行構築（AGENTS.md の Commonization rule に従う）

## 5. 課題台帳の様式

`refine-03-issue-catalog.md` は以下の列で構成する。

| 列 | 内容 |
| --- | --- |
| ID | `MDE-nnn` |
| 分類 | 不具合 / 体験改善 / 品質・保守 / 基盤 / 新機能 |
| 事象 | 利用者から見た症状（1〜2文） |
| 原因 | コード上の該当箇所（`ファイル:行`）と原因の要約 |
| 影響 | 誰のどの操作が困るか |
| 規模 | S（1日以内）/ M（数日）/ L（1週間超） |
| 土台性 | 高 / 中 / 低 |
| 優先度 | 高 / 中 / 小 / 対象外 |
| 配属 | Phase 2 / 3 / 4 / 5 / 対象外 |
| 備考 | 依存関係、判定理由 |

「原因（ファイル:行）」まで埋めることを必須とする。ここが埋まっていれば、Phase 2 以降の実装 Issue は調査から始めずに済む。

### 台帳の初期投入元

- 利用者からの改善要望 5 件（印刷、レイアウト、Undo、コードブロック、表デザイン）
- 現状分析で検出した技術課題 13 件（サニタイズ、CDN 依存、責務分割、保存、狭幅対応 ほか）
- Phase 1 の追加分析で新たに検出したもの

## 6. 優先度判定基準（確定: 4軸モデル）

> 基準を先に合意してから当てはめる。逆順にすると結論の後付けになる。（決定: Issue #51）

### 6-1. 優先度（4軸モデル）

```text
■ Step 1: ゲート条件（該当すれば即・優先度-高。規模や閲覧貢献度で薄めない）
  a) 現在すでに壊れている（利用者が期待どおりに使えない）
  b) コンセプト実現の中核である（主用途 C を成立させる施策そのもの。規模を問わない）
  c) 安全性・可用性に関わる（外部依存の破壊的変更、未サニタイズ等）

■ Step 2: ゲート非該当の課題を判定する 2 軸マトリクス

                        | 開発規模：軽量(S) | 開発規模：重量(M〜L)
  閲覧体験向上：高      | 優先度-高（クイックウィン） | 優先度-中（計画的投資）
  閲覧体験向上：低      | 優先度-小                   | 対象外の候補

■ Step 3: 土台性（独立軸・Phase 振り分け専用。従来どおり）
  土台性-高 → 優先度に関わらず Phase 2 へ配属
```

> **旧基準からの変更点（Issue #51）**
> - b) を「コンセプト実現の必須要素かつ規模 M 以下」→「コンセプト実現の中核（規模を問わない）」へ変更。これにより `MDE-003` のような規模 L の施策も優先度-高になり得る
> - 旧・優先度-中/小 の判定を「開発規模 × 閲覧体験向上度」の 2 軸マトリクスへ明確化

### 6-2. 土台性（Phase 2 / Phase 3 の振り分け軸）

```text
土台性-高 = 2 件以上の他課題がこの完了を前提とする、
            または後回しにすると同一箇所の作り直しが発生する
            → 優先度に関わらず Phase 2 へ配属する

土台性-中 = 1 件の他課題が前提とする
            → Phase 2 / 3 のどちらでも可。規模で判断

土台性-低 = 独立して実施できる
            → 優先度に従って Phase 3〜5 へ配属
```

### 6-3. コンセプト適合チェック

すべての「新機能」分類の課題に対し、以下を確認して台帳の備考へ記録する。

1. 3-2 で決めた主用途に貢献するか
2. 3-3 の「シンプル」の定義に違反しないか
3. 既存機能で代替できないか

3 つのうち 1 つでも満たさない場合は、優先度-小 または 対象外 とする。

## 7. 成功指標（Phase 6 で測定）

Phase 1 で確定させ、Phase 6 のまとめを「やったことの列挙」ではなく「達成の検証」にする。静的アプリのため、測定可能なものに限定する。

| # | 指標 | 判定方法 |
| --- | --- | --- |
| 1 | A4 換算 10 ページ相当の Markdown が、HTML エクスポート・PDF 出力ともに全ページ印刷できる | 実測（印刷プレビューのページ数） |
| 2 | 主要な装飾操作がキーボードのみで完結する | 対象操作リストに対する Yes/No |
| 3 | ネットワーク遮断状態でアプリが起動しプレビューが描画される | 実測（オフライン再現） |
| 4 | 表を含む文書の作成が、Excel からのコピペを起点に完結する | シナリオ実演 |
| 5 | Playwright テストが主要機能の回帰を検出できる | 対象機能リストとテスト件数 |
| 6 | 閲覧モード（既定）の常時表示操作要素が **5 個以内** であること | 実数カウント |
| 7 | 利用者が設定する項目の増加数が 0（または合意した上限以内） | 実数カウント |

指標 6 は閲覧モード（既定画面）の `N_read = 5` に対応。指標 7 は「シンプルさの維持」の設定面を数値で縛るためのもの。（3-3 確定値を反映: Issue #51）

## 9. 制約・前提（AGENTS.md 準拠事項）

- 変更は原則 `apps/markdown-editor/` 内に閉じる。他アプリを「ついでに」変更しない
- アプリ機能改修とモノリポ基盤改修を同一 PR に混在させない
- Issue に明示されていない変更へ独断でスコープを拡張しない
- 開発環境は Node.js 24 / npm 11、標準起動は `npm run dev --workspace=markdown-editor`（`http://127.0.0.1:8000/`）
- 検証結果は `passed` / `attempted but blocked` / `failed` / `not run` を区別して記録する
- GitHub Pages のサブパス `/pocketly/` を前提とし、相対パスを優先する
- `packages/` `shared/` `common/` を先行作成しない

## 付録B. 用語

| 用語 | 定義 |
| --- | --- |
| Refine | 本 PJ。既存アプリの洗練を指し、新規開発や作り直しを含まない |
| 土台性 | ある課題の完了が、他の課題の前提になる度合い |

| 将来構想 | 本 Refine では実装しないが、方向性として記録する構想 |
| 基盤整備 | 利用者から直接は見えないが、複数の後続改修の前提となる整備 |

# Markdown Editor – 将来構想

> 状態: **確定**（確定日: 2026-07-28 / 根拠 Issue: #57）
> 配置先: `apps/markdown-editor/docs/refine-04-vision.md`

## この文書の運用ルール

**発想の発散は Lv2-D で一度きり。以降の Phase では追記のみとし、発散の場を持ち越さない。**

Phase 3〜5 の実施中に新しいアイデアが出た場合は、本文書へ追記して「本 Refine 対象外」と明示する。実装スコープへ取り込む判断は行わない（スコープ膨張を防ぐため）。

各構想には Lv2-D で以下を付与する。

- **判定**: 扱う / 扱わない
- **理由**: 判定の根拠（1 行以上）
- **紐づけ**: 「扱う」場合は対応する `MDE-nnn`

## 前提: 移行が起きていない理由の分解

「Excel / Word から Markdown へ移行できていない」という課題を、3 つの障壁に分解する。構想の評価軸として使う。

| 障壁 | 内容 | 対応する構想 |
| --- | --- | --- |
| (a) 出力品質 | 配布物としての見栄えが Word に負ける | C |
| (b) 表の編集 | Excel / Word の表編集に対する劣位 | A の一部、B |
| (c) 書き心地 | 入力効率と快適さ | D |
| (d) 資産の分断 | 既存資産が Office 側にあり、移行は片道切符に見える | A（一部）／H（本 Refine スコープ外） |

**(d) が最も見落とされやすい。** 「移行」ではなく「併用」から始められれば心理的障壁は大きく下がる。

## A. Office との往復

| 構想 | 内容 | 規模 | 判定 |
| --- | --- | --- | --- |
| A-1 | Excel からの貼り付けを Markdown 表へ変換 | M | **保留**（`MDE-019` は対象外の候補。Phase4 先頭 Lv2「軽量ファイルマネージャの採否と Charter 改定要否を判断する」で再判断） |
| A-4 | Markdown 表 → CSV/TSV コピー（逆方向） | S | **扱う（候補）**（規模 S、低リスク、UI 要素増加なし） |

**論点**

A-4 は規模 S ながら「Markdown で作った表を Excel へ戻せる」という往復を成立させる。A-1 とセットで検討する価値がある。

※ 旧 A-2（docx 取り込み）・旧 A-3（docx 書き出し）は H 節（H-1・H-2）へ移動した。

## B. レビュー体験

Word の「コメント」「変更履歴」に相当する機能。資料は書いて終わりではなくレビューされるため、実務上の移行障壁として大きい。

| 構想 | 内容 | 規模 | 判定 |
| --- | --- | --- | --- |
| B-1 | プレビュー上での注釈コメント（`<!-- comment: -->` として本文に保持） | L | **扱わない**（共同編集に隣接、Charter 非目標と近接） |
| B-2 | ローカルスナップショット履歴と差分表示（Git を使わない簡易版） | L | **保留**（`MDE-011` の方針決定と設計が重なる。Phase3 完了後に評価） |
| B-3 | 前回保存からの変更箇所ハイライト | M | **保留**（同上） |

**論点**

B-1 は Markdown ファイルの互換性を損なわない形（HTML コメント）で実現できるが、他ツールで開いた際にコメントが可視化されない。B-2 は `MDE-011`（作業内容の永続化）と設計が重なるため、`MDE-011` の方針決定後に評価すべき。

## C. ドキュメント品質

| 構想 | 内容 | 規模 | 判定 |
| --- | --- | --- | --- |
| C-1 | A4 ドキュメントテーマ（表紙・見出し番号・ページ番号・目次ページ） | L | **保留**（`MDE-021` は対象外の候補。Phase4 先頭 Lv2 で再判断） |
| C-2 | 印刷プロファイル（社内文書用 / 技術文書用などのプリセット） | M | **扱わない**（シンプルさ違反：設定項目増加） |
| C-3 | 数式表示（KaTeX） | M | **扱わない**（依存追加、需要未確認） |
| C-4 | 脚注 | S | **扱う（候補）**（規模 S、閲覧品質へ直接寄与） |

**論点**

C-2 は設定項目の増加に直結するため、Charter §3-3 の「シンプル」の定義と正面から衝突する。C-1 が入るならプリセットは 1 つに固定し、選択肢を持たせない設計もありうる。

C-3 は依存が 1 つ増える（`MDE-008` の方針に従う必要がある）。利用者層に数式需要があるかを先に確認すること。

## D. 書き心地・楽しさ

| 構想 | 内容 | 規模 | 判定 |
| --- | --- | --- | --- |
| D-1 | キーボードショートカット | S | → `MDE-015` |
| D-2a | 検索（文書内検索、正規表現対応前提） | M | 扱う → `MDE-018` |
| D-2b | 置換（文書内置換、D-2 から分離） | M | 扱う → `MDE-028` |
| D-3 | 目次のドラッグによる章の並べ替え | L | **保留**（`MDE-022` は対象外の候補。Phase4 先頭 Lv2 で再判断） |
| D-4 | スラッシュコマンド（`/table` `/mermaid` 等で即挿入） | M | **扱わない**（既存 Templates 機能との役割重複） |
| D-5 | 貼り付け時の自動整形（URL → リンク、画像 → Base64 埋込） | M | **扱う（候補）**（既存論点で効果大と評価済み） |
| D-6 | スニペット・定型文 | M | **扱わない**（既存 Templates 機能との役割重複） |
| D-7 | プレゼンモード（`---` 区切りでスライド表示） | L | **扱わない**（アプリの性格が変わる） |
| D-8 | サイドバー型グローバルナビ（折りたたみ式レール） | L | 扱う → `MDE-003` へ統合 |

**論点**

D-3 は Word にない体験であり、「操作して楽しい」という要件に対する最有力候補。目次を「移動手段」から「構造編集手段」へ格上げする発想。

D-5 の画像部分は既存の Insert Image 機能をペースト経路へ拡張するだけで実現でき、規模の割に効果が大きい。

D-6 は既存の Templates 機能と役割が重なる。Charter §6-3 の「既存機能で代替できないか」に該当する可能性が高い。

D-7 はアプリの性格を変える。Pocketly に別アプリとして立てるほうが適切かもしれない。

D-8 は `MDE-003` のモード制レイアウト設計の一部として取り込む。折りたたみ式サイドバーレールは横ツールバーと比べ機能格納と圧迫感軽減を両立できる可能性があり、閲覧モード（N_read=5）の制約を満たしながらナビゲーション要素を格納する手段として有効。詳細 UI 設計は Phase 3 の Lv3 設計時に確定する。（Issue #51）

## E. 文書を「1 枚」から「束」へ

| 構想 | 内容 | 規模 | 判定 |
| --- | --- | --- | --- |
| E-1 | 軽量版ファイルマネージャ（ドラッグ&ドロップ複数ファイル読込、一覧からの切替プレビュー） | L | **保留**（主用途 C 確定後の再検討候補。Phase4 先頭 Lv2 で採否・Charter 改定要否を判断） |
| E-2 | 文書間リンクとバックリンク | L | **扱わない（推奨）** |
| E-3 | 横断検索 | L | **扱わない（推奨）** |

**E-1 の判定について**

軽量版の範囲（含める）：ドラッグ&ドロップによる複数ファイル読込 / ファイル一覧からの切替プレビュー（セッション限定）/ D-2a（grep 検索）と連携した複数ファイル横断検索。

軽量版の範囲（含めない）：永続化、文書間リンク・バックリンク、横断編集・一括保存（元 E-1 が対象外と判定した核心部分）。

手続き上の注意：軽量版であっても Charter §3-4「非目標」の複数ファイル管理に触れるため、「対象外」への機械的な追認ではなく「主用途 C 確定後の再検討候補」として記録するに留める。

**E-2・E-3 の推奨判定の理由**

ここに踏み込むとアプリの性格が「エディタ」から「ドキュメント管理ツール」へ変わる。Pocketly の「小さく、軽く、すぐ使える」という前提と正面衝突する。Charter §3-4 で既に非目標として挙げている領域。

**ただし、この判断を記録すること自体に価値がある。** 将来 Pocketly の方針が変わった際、なぜ見送ったかを追跡できる。

## F. Pocketly 内での連携

| 構想 | 内容 | 規模 | 判定 |
| --- | --- | --- | --- |
| F-1 | Markdown 内の CSV ブロックを csv-gantt-viewer で描画 | L | **扱わない（推奨）** |
| F-2 | restructuredtext-editor との相互変換 | L | **扱わない（推奨）** |
| F-3 | 共通ドキュメントテーマのアプリ間共有 | M | **扱わない（推奨）** |

**推奨判定の理由**

`AGENTS.md` の Commonization rule により `packages/` `shared/` `common/` の先行作成は禁止されている。実需が確認され、対象 Issue が明示的に共通化をスコープへ含める場合にのみ実施できる。本 Refine のスコープでは実需が確認できていない。

また `AGENTS.md` は「対象アプリ以外を『ついでに』変更しない」ことをアプリ境界のルールとして定めており、これらの構想はいずれも複数アプリへの変更を伴う。

## G. 基盤

| 構想 | 内容 | 規模 | 判定 |
| --- | --- | --- | --- |
| G-1 | 外部依存の固定・オフライン動作 | M | → `MDE-008` |
| G-2 | PWA 化（インストール可能、完全オフライン） | M | **扱わない**（モノリポ基盤側の判断が必要、本 Refine スコープ外） |
| G-3 | ダークモード | M | → `MDE-016` |
| G-4 | 自動保存と復元 | M | → `MDE-011` |

**論点**

G-2 は `MDE-008` で vendor 同梱を選んだ場合の自然な延長線上にある。ただし Service Worker の導入は GitHub Pages のサブパス（`/pocketly/`）配下でのスコープ設定に注意が必要で、他アプリへの影響も生じうる。モノリポ基盤側の判断が必要になるため、本 Refine のスコープ外とする可能性が高い。

## H. 本 Refine スコープ外の別アプリ候補

> F 節（Pocketly 内での連携）は既存アプリ間の連携を扱う。
> H 節は、Markdown Editor の機能拡張ではなく、将来的に Pocketly の
> 新規アプリとして検討しうる候補を記録する。

| 構想 | 内容 | 規模 | 判定 |
| --- | --- | --- | --- |
| H-1（旧 A-2） | docx 取り込み（Word → Markdown） | L | 扱わない（推奨） |
| H-2（旧 A-3） | docx 書き出し（Markdown → Word） | L | 扱わない（推奨） |
| H-3（旧 A-5） | Excel 文書フォーマット（見積書・チェックリスト等）ごとの専用 Web 入力 UI | L | 扱わない（推奨） |

**推奨判定の理由**

本アプリのコンセプトは「参照と編集」であり、変換・フォーマット別 UI は本質的にオプション機能である。特に H-1（to-MD 方向）は、Word の複雑な書式（表の結合、脚注、変更履歴、スタイル階層等）をどこまで Markdown へ写像するかという設計判断が発散しやすく、「Markdown Editor に機能追加する」規模を超えて「専用ツールを作る」規模の話になる。H-3 も同様に、フォーマットの数だけ小さなアプリを作る話に発展し、Markdown Editor の規模を超える。

脱 Office という展望自体は否定しないが、これらを Markdown Editor へ抱え込むと Refine 全体のスピード・リソースを損なう。**アイデア自体は消さず、将来 Pocketly 全体として新規アプリを検討する際の種として本節に記録するに留める。** 詳細検討（要件定義・規模見積もり）は本 Refine のスコープ外。

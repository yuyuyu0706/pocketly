## 1. プロジェクト概要

| 項目 | 内容 |
| --- | --- |
| PJ名 | Markdown Editor Workspace（MEW） |
| ブランド名 | Markdown Editor Blue（MERから継続） |
| 対象アプリ | `apps/markdown-editor2/`（新設。MERのコード一式をコピーして初期状態とする） |
| 旧PJ | Markdown Editor Refine（MER）＝`apps/markdown-editor/`。凍結済み・本番稼働継続・変更禁止（Issue #85） |
| 期間 | 2026-08 〜 |
| 管理単位 | Lv1 Issue = GitHub Milestone = Phase |
| 課題ID体系 | ⚠作業用デフォルト（要利用者確認）: `MEW-nnn`（連番、Phase をまたいで一意）。MERから引き継ぐ保留テーマは新IDを採番し、備考に旧ID（`MDE-nnn`）を記録する。台帳作成（Lv2-3）前に確定する |
| 文書配置 | `apps/markdown-editor2/docs/workspace-*.md` |

### 背景

MER は単一文書ビューアとして高い完成度（モード切替・フローティングパネル・PiP
サブウィンドウ化・簡易保存・リロード復元・ToC磨き込み）に達した。一方、実利用
（PiPサブウィンドウ化）を通じて「複数ファイルを同時に扱えない窮屈さ」が、単一
文書ビューアの快適さより強く体感される本質的課題として判明した。

複数文書ワークスペース化は MER 憲章で正式に「非目標」と決議済み（Issue #51）の
性質転換にあたるため、MER を凍結し、新 PJ「MEW」として独立させた。

### PJ ゴール（最終 Phase 到達時の姿）

1. フォルダごと持ち込んだ 10 個超の Markdown 文書群を、ストレスなく俯瞰・
   閲覧・行き来できる状態になっている
2. 「Markdown 文書群を読むならこれ」と感じられる体験上の武器（俯瞰系）が
   最低ひとつ確立している
3. 出所を精査していないファイル群を開いても安全な状態（サニタイズ）が
   成立している
4. 追加改修が安全に行える構造（複数ウィンドウ前提の設計規約・テスト）に
   なっている
5. 本 PJ でやらないと判断した構想が、判断理由とともに記録されている

## 2. Phase 構成（Milestone 対応）

Phase 1 のみ確定。Phase 2 以降の詳細スコープは `workspace-05-phase-plan.md` で
確定するが、以下を骨格の仮置きとする（MER の「基盤整備 → 体感価値」の切り分け
方針を踏襲）。

| Phase | 位置づけ | 主種別 |
| --- | --- | --- |
| 1 | 意思決定と計画確定。**機能面のコード変更なし** | Docs |
| 2 | 基盤整備：**ゲート条件（サニタイズ）**＋ワークスペース土台（フォルダ・ツリー・タブ）＋保存戦略 | Platform / Feature |
| 3 以降 | 俯瞰の中核（横断検索・横断ToC）→ 行き来の強化 → 後続レイヤー（PiP参照・分割等） | Feature |
| 最終 | 成果検証と記録 | Docs |

### Phase 2 と Phase 3 以降の切り分け方針

- **Phase 2 に入るもの** — ゲート条件該当（サニタイズ）、および複数の後続課題が
  その上に乗る土台（ワークスペース基盤・保存戦略・複数ウィンドウ設計規約）
- **Phase 3 以降に入るもの** — 利用者が挙動の変化を体感できるもの

判定に迷う課題は「土台性」評価で決める（§6）。

## 3. コンセプト定義（確定: 2026-08-08 対話）

### 3-1. コンセプト文（確定）

> **MEW は、フォルダごと放り込めるローカル完結の Markdown 文書リーダーである。**
> 文書群を丸ごと持ち込み、ツリー・横断検索・横断ToCで全体を俯瞰し、タブで
> 素早く行き来しながら「読む」ことを既定とする。編集は従。
> ブラウザで開けばすぐ使え、ビルドもログインも要らない。

MEW の自画像は「Markdown エディタの多文書化」ではなく「**文書群のリーダー／
ブラウザ**」である。

### 3-2. 想定利用者と体験の優先順位（確定）

フォルダ単位で管理された **10 個超**の Markdown 文書群を丸ごと持ち込み、全体を
俯瞰しながら目的の文書へ素早く行き来して読む・書く利用者。個別ファイルだけの
軽い持ち込みにも対応する。

| 順位 | 体験 | 設計上の帰結 |
| --- | --- | --- |
| 1 | **俯瞰する**（ツリー・横断検索・横断ToC） | MEW の本丸。差別化の中核 |
| 2 | **行き来する**（タブ・クイックスイッチャー） | 俯瞰と一体の基盤動線 |
| 3 | 参照しながら書く（PiP参照・分割ビュー） | 後から足すレイヤー。目玉としない |

持ち込み方式は「フォルダごと開く」「個別ファイルを都度開く」の**両対応**とする。

### 3-3. 「シンプル」の定義（確定）

MEW の「シンプル」の柱は以下の 2 つとする。

1. **開いてすぐ使える**: ビルド不要・ログイン不要・ローカル完結
2. **閲覧既定・編集は従**: MER 主用途 C の思想を継承。第一に「読む」道具

判断可能な基準への展開:

- **設定のシンプルさ**: 利用者が設定する項目を増やさない。増やす場合は既定値の
  ままで成立させる（MER から継承）
- **機能のシンプルさ**: 機能を 1 つ足すときは、代替できる既存機能がないかを
  必ず確認する（MER から継承）
- **判断基準**: 初見の利用者が説明なしに使えるか（MER から継承）
- **画面のシンプルさ（常時表示操作要素の上限）**: MER の `N_read = 6` は
  そのまま適用しない。ワークスペース UI 再構成（§3-4）が解禁されたため、
  数値上限はワークスペース UI 設計案の確定時（Phase 2 冒頭の Lv2）に再設定
  する。それまでは上記 3 原則で判断する

### 3-4. UI 構造の扱い（確定）

**ワークスペース最適化のためなら UI 再構成してよい。**
MER からコピーした初期コードは「資産」であって「制約」ではない。MER の UI 構造
（フローティングパネル等）の維持は成功指標に含めない。俯瞰前提でレイアウトを
ゼロベースで設計してよい。

### 3-5. 非目標（Non-Goals）（確定）

| 非目標 | 理由 | 記録先 |
| --- | --- | --- |
| プラグイン・拡張機構 | シンプル原則。IDE 化・基盤化しない | — |
| Markdown 以外の形式対応 | Markdown 文書群に特化する | — |
| クラウド同期・共同編集 | 柱「ローカル完結」と矛盾するため扉を閉じる | — |
| `packages/` `shared/` 等の共通化基盤の先行構築 | AGENTS.md の Commonization rule に従う（MER から継承） | — |

**将来構想（非目標ではなく扉を開けておくもの）**: ノート DB 化（タグ・
メタデータ・グラフビュー等）。「俯瞰する」の延長線上にあるため
`workspace-04-vision.md` に記録し、本 PJ の対象外であることを明示する。

## 6. 優先度判定基準（確定: 4軸モデル＋MEW調整）

MER の 4 軸モデル（ゲート条件 → 2 軸マトリクス → 土台性）を再利用する。
MEW 固有の調整は以下の 2 点。

### 6-1. 優先度（4軸モデル・MEW版）

```text
■ Step 1: ゲート条件（該当すれば即・優先度-高）
  a) 現在すでに壊れている（利用者が期待どおりに使えない）
  b) コンセプト実現の中核である（俯瞰・行き来を成立させる施策そのもの。規模を問わない）
  c) 安全性・可用性に関わる（外部依存の破壊的変更、未サニタイズ等）
     → 【MEW確定事項】サニタイズ（旧MDE-007）は c) 該当としてゲート条件に
       昇格済み。俯瞰系機能（横断検索・横断ToC等）の着手前に実施する。
       フォルダ丸ごと＝出所を精査していないファイルを一括で開く前提のため

■ Step 2: ゲート非該当の課題を判定する 2 軸マトリクス
  ※「閲覧体験向上」軸は MEW では「俯瞰・閲覧体験向上」と読み替える

                          | 開発規模：軽量(S) | 開発規模：重量(M〜L)
  俯瞰・閲覧体験向上：高  | 優先度-高（クイックウィン） | 優先度-中（計画的投資）
  俯瞰・閲覧体験向上：低  | 優先度-小                   | 対象外の候補

■ Step 3: 土台性（独立軸・Phase 振り分け専用。MER 定義のまま）
  土台性-高 → 優先度に関わらず Phase 2 へ配属
```

### 6-2. 「ワークスペース基盤への依存度」軸（保留・台帳作成時の宿題）

新規軸として今は追加しない。**Phase 1 で課題台帳を作りながら要否を判断する。**
既存の「土台性」で表現しきれない依存（タブ基盤の上にしか作れない機能等）が
多発した場合に軸追加を再検討する。

### 6-3. コンセプト適合チェック（MER から継承）

すべての「新機能」分類の課題に対し、①主用途（俯瞰・閲覧）への貢献 ②「シンプル」
定義への違反有無 ③既存機能での代替可否 を確認して台帳の備考へ記録する。1 つでも
満たさない場合は優先度-小または対象外とする。

## 9. 制約・前提

### 9-1. AGENTS.md 準拠事項（MER から継承）

- 変更は原則 `apps/markdown-editor2/` 内に閉じる。他アプリを「ついでに」変更しない
- `apps/markdown-editor/`（MER）には一切変更を加えない
- アプリ機能改修とモノリポ基盤改修を同一 PR に混在させない
- Issue に明示されていない変更へ独断でスコープを拡張しない
- 検証結果は `passed` / `attempted but blocked` / `failed` / `not run` を区別して記録する
- GitHub Pages のサブパス `/pocketly/` を前提とし、相対パスを優先する
- `packages/` `shared/` `common/` を先行作成しない

### 9-2. MEW コーディング原則（MER の教訓の規約化）

1. **document/window の動的解決**: `document`／`window` をモジュール読み込み
   時点の値で固定参照しない。DOM 要素起点で `element.ownerDocument`／
   `element.ownerDocument.defaultView` 経由で解決する。
   （根拠: MER の PiP 開発で発見した不具合 19 件中 9 件が同一パターン。複数
   ウィンドウ・複数ペインが標準となる MEW では最重要原則。PR レビュー観点に
   含める）
2. **スタイル上書きは明示的な値で行う**（詳細度起因の暗黙挙動を避ける）
3. **テストは実関数・実変数を `window.__xxx` 形式で公開して直接検証する**
   （テスト内ロジック再実装による「見せかけのテスト」を禁止）
4. **PR 説明文の自己申告を鵜呑みにせず、必ず実差分で確認する**（レビュー原則）
5. **CI で検証できないウィンドウ系機能（PiP 等）は、手動確認チェックリストを
   PR に添付する**

## 10. リスクと対応

| リスク | 影響 | 対応 |
| --- | --- | --- |
| File System Access API 非対応環境（Brave 等）で中核体験が成立しない | 利用者の分断 | `<input webkitdirectory>` による読み取り専用フォールバックを Phase 2 の保存戦略設計に含める（閲覧完全動作・保存はダウンロード方式） |
| 文書数増加で俯瞰系（ツリー・横断検索・横断ToC）が重くなる | 中核体験の毀損 | パフォーマンス設計（遅延読み込み・インデックス化）を台帳に最初から登録し、成功指標に応答時間を含める |
| 出所不明ファイルの一括読み込みによる XSS | 安全性 | サニタイズをゲート条件に昇格済み。俯瞰系着手前に実施 |
| UI 再構成の解禁がスコープ膨張を招く | 遅延 | 再構成は「俯瞰・行き来の成立に必要な範囲」に限定し、Lv2 Issue の対象範囲に明記する |
| 将来構想（ノート DB 化等）が Phase に混入する | スコープ膨張 | `workspace-04-vision.md` 記載項目は台帳で「対象外」と明示的に紐づける |
| MER との二重管理コスト（不具合の逆輸入判断等） | 運用負荷 | MER は変更禁止を原則とし、逆輸入は MEW 成熟後に一括判断する（Issue #85 の方針を維持） |

| Workspace | 本 PJ。フォルダ単位で持ち込んだ文書群を俯瞰・閲覧・行き来する作業空間 |
| 俯瞰 | ツリー・横断検索・横断ToCにより文書群の全体を見渡すこと。MEW の第一体験 |
| ゲート条件 | 優先度判定で他の軸に先立って「優先度-高」を確定させる条件。MEW ではサニタイズが該当 |
| 土台性 | ある課題の完了が、他の課題の前提になる度合い（MER から継承） |
| 将来構想 | 本 PJ では実装しないが、方向性として記録する構想（例: ノート DB 化） |
| 逆輸入 | MEW で実装した機能を MER（`apps/markdown-editor/`）へ移植すること。MEW 成熟後に一括判断 |
